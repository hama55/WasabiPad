# 連携先ウィンドウを起動直後にベストエフォート配置する

## Context

連携エディタと連携プレビューは第2段階で設定・明示起動まで分離できた。次に、起動したアプリを対応するWasabiPadのペイン付近へ置くことで、ファイルビュー側と編集・プレビュー側を同時に使いやすくする。ただし、外部アプリのウィンドウはTauriの`Window` APIでは直接管理できず、既存プロセスの再利用やCLI経由の起動もある。

## Decision

- Windowsの`CreateProcessW`が返す直下プロセスIDだけを使い、可視トップレベルウィンドウを最大2秒だけ探索する。
- 見つかったウィンドウを、連携エディタは`editorHost`、連携プレビューは`previewEl`の物理画面矩形へ一度だけ配置する。
- DPI倍率とWebViewの画面位置を使ってCSS矩形を物理ピクセルへ変換する。
- `SetForegroundWindow`はベストエフォートとし、Windowsの前面化制限で失敗しても起動失敗にはしない。
- 起動直後に`ShowWindow(SW_RESTORE)`で最小化状態を表示へ戻すが、利用者向けの最大化・最小化操作や状態管理は提供しない。
- ウィンドウ未検出・配置失敗でも外部プロセスは終了させず、WasabiPadから通知する。
- 連携先ウィンドウをWasabiPadへ埋め込まない。WasabiPadの編集側ステータスバーは残す。
- 移動・リサイズへの継続追従、最大化・最小化操作、終了、子孫プロセス探索、既存プロセスの再利用・終了管理は行わない。
- 外部アプリを直接起動しないコマンドでは、連携先ウィンドウを特定できず配置されない場合がある。

## Consequences

明示起動時の初期配置だけで利用体験を改善でき、外部アプリが固まってもWasabiPad側に継続的な監視や同期処理を持ち込まない。配置に失敗しても外部アプリを利用できる。一方、`cmd`、`start`、CLI委譲、既存プロセス再利用では配置できない場合がある。

## Rejected alternatives

- 外部アプリをTauriの子ウィンドウへ埋め込む: アプリごとの差が大きく、安定性と互換性を損なう。
- 連携先ウィンドウをWasabiPadの移動・リサイズへ継続追従させる: ポーリングとライフサイクル管理が必要で、第3段階の最小目的を超える。
- PIDの子孫探索や既存プロセスの再利用: 無関係なウィンドウを操作するリスクがある。
